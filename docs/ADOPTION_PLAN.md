## 0. Purpose

A first implementation of this project already exists. It was generated by a different AI coding agent (freebuf) from an earlier, smaller prompt. We will **not rebuild from zero**. We will:

1. adopt that code into this repository,
2. audit it against the Master Spec and the Honesty Rules,
3. fix what is wrong,
4. evolve it, phase by phase, into the target system.

Authority order: Honesty Rules, then the Master Spec, then this plan, then the existing code. The existing code is a draft, not a reference.

## 2. Principles for brownfield work

1. **Do not rewrite what works.** Fix and refactor in place. Rewrite only with a recorded reason.
2. **Characterization tests first.** Before restructuring a module, pin its current behavior with golden tests (Appendix A), unless the behavior is itself a defect.
3. **Small reversible steps.** One logical change per commit, tests green at every commit.
4. **Defects that break honesty or physics come first**, before any feature work.
5. **Verify external APIs** against the installed versions. Generated code often calls APIs that do not exist or have changed.
6. **Old code has no authority.** If code and spec disagree, the spec wins, and the difference is logged.
7. **One phase per session.** Keep sessions short and resumable. State lives in files (`docs/PROGRESS.md`), not in conversation history.
8. **Decision log.** Every keep, refactor, rewrite or deletion decision is written to `docs/audit/DECISIONS.md` with a reason.

## 4. Keep, refactor or rewrite: decision rules

| Verdict | When | Action |
|---|---|---|
| `KEEP` | Correct, tested or easily testable, matches contracts | Leave. Add tests |
| `REFACTOR` | Logic is right, structure or naming or location is wrong | Characterization tests, then move and clean |
| `FIX` | Small defects, wrong numbers, missing labels | Fix with a test that fails before and passes after |
| `REWRITE` | Violates an Honesty Rule at the design level, physically wrong approach, or cheaper to redo than to fix | Record reason, write replacement behind the same interface, delete old only after the replacement passes the same tests |
| `DROP` | Not in the Master Spec and not useful | Record, remove in a separate commit |

Severity scale for findings:

| Level | Meaning | Examples |
|---|---|---|
| S0 | Blocks trust | Truth leaks into the stream, invented probabilities, number shown without a label, non-determinism, wrong hydraulics, missing banner |
| S1 | Major | API calls that do not exist, tests absent for core logic, false alarms on normal runs, double counting in costs |
| S2 | Moderate | Missing contract fields, hard-coded constants, poor structure, weak error handling |
| S3 | Minor | Style, naming, comments |

## 6. Audit checklist per area

Used in Phase A0. For each item record `OK`, a finding with severity, evidence (`file:line` or command output), and a verdict.

### 6.1 Network and scenarios
- Network is deterministic for a given seed. `network_version` is a content hash.
- Connectivity, no isolated junctions, units documented (head in metres, flow in m3/h).
- Minimum pressure at peak demand is acceptable. Tanks do not overflow or starve over a 7-day normal run.
- A `NetworkProvider` abstraction exists, or note its absence.
- Scenario schema: validated ranges, unknown fault types rejected, times inside the horizon, versioned.

### 6.2 Simulation (WNTR)
- Every WNTR call exists in the installed version (introspect, do not trust).
- Pressure-driven demand is actually enabled and the chosen simulator supports it with leaks.
- Pipe leaks: split-node approach is correct (flows conserved, leak area units correct).
- Gradual leaks: piecewise chunking hands over tank levels and pump states between chunks. A chunk-size convergence check exists or is noted missing.
- Pump outage and standby switching work and are tested.
- Fault-free baseline run uses the same demand settings, and this assumption is documented.
- Runtime for a 48 h run is measured.
- Same config plus seed gives identical output (hash it twice).

### 6.3 Sensors and stream
- Noise is seeded. Drift, stuck, dropout, offset behave as described. Dropout produces missing readings, not zeros.
- **Truth never appears in the stream or in detector inputs.** Search the code for every place truth and hidden fault tags are read.
- Message format matches the contract. Pause, resume, speed, seek work.

### 6.4 Quality, detection, incidents
- Thresholds are configurable. Each check has a unit test.
- Residuals are normalized with sigma estimated from fault-free runs. Persistence or CUSUM exists.
- False alarms on `normal`, `holiday`, `heatwave` over at least 5 seeds. Record the count.
- Diagnosis returns `unknown` for ambiguous cases. No percent confidence without a defined statistic.
- Incident grouping yields one incident per root cause. Merge and split behavior is tested.

### 6.5 Impact, finance, decision, evidence
- Impact runs start from a state snapshot on copies of the network.
- Each money line equals one physical quantity times one unit price. No double counting.
- Assumptions have unit, range, version and verified flag. No invented probabilities presented as findings.
- Monte Carlo output is labeled "conditional on assumed ranges".
- Decision engine includes break-even and sensitivity. A scenario with negative benefit recommends `monitor`.
- Every number the UI shows has an evidence record and a label. No LLM in calculations.

### 6.6 API, storage, frontend, ops
- Endpoints match the contract. Errors are structured. No truth over WebSocket.
- Time series are stored in a way that scales to long runs. Run manifests exist.
- Frontend: honesty banner on every page, label chip on every number, "show twin truth" toggle separate from operator view, no CDN dependencies, builds cleanly, no hard-coded demo numbers.
- `docker compose up` works offline. README commands work from a fresh clone.
- Tests exist, are meaningful, and pass. Linting and type checks run.
- Secrets, licenses and dependency pinning reviewed.

## 9. Phases

Each phase ends with an exit gate. Do not start the next phase until it passes. Master Spec milestones are in Section 21 of the spec.

### Phase A0: Baseline and audit (no code changes)
**Tasks:** tag baseline, install and run, run tests, inventory, audit using Section 6, write the four deliverables in Section 7.
**Exit gate:** `INVENTORY.md`, `AUDIT.md`, `DECISIONS.md`, `MAPPING.md` exist and are reviewed by the human. Measured numbers recorded.

### Phase A1: Stabilize and fix S0 and S1
**Tasks:**
1. Add characterization tests (Appendix A) for behavior that is correct.
2. Make `make test-backend`, `make test-frontend`, `make dev` and `make up` work from a fresh clone.
3. Fix all S0 findings, then S1 findings. Each fix has a test that failed before.
4. Extract contracts from existing pydantic models into `contracts/` (JSON Schema) and generate TypeScript types. Add a CI check for drift.
5. Add the honesty banner, label chips and Fidelity badge where missing (placeholder text is fine until F1 geometry exists).
**Exit gate:** tests green, determinism verified, truth leak impossible (a test proves telemetry and stream contain no truth fields), zero incidents on `normal`, `holiday`, `heatwave` over 5 seeds, no S0 or S1 remaining.

### Phase A2: Restructure to the target architecture
**Tasks:**
1. Create `platform/`, `domains/water/`, `contracts/`, `assumptions/`, `docs/adr/`.
2. Move modules per the mapping in small `git mv` commits, tests green after each.
3. Introduce the `DomainAdapter` interface and wrap the existing water code in `domains/water`. Add the conformance test skeleton and the lint rule that `platform/` never imports `domains/`.
4. Add the `ug` CLI skeleton (`ug doctor`, `ug run`), GitHub Actions CI, and root `CLAUDE.md` commands section.
5. Write ADR-001 to ADR-010 stubs (titles in Master Spec Appendix D).
**Exit gate:** golden tests unchanged, CI green, import rule enforced, app runs as before.

### Phase B1 (Spec M1): Twin core upgrade
**Tasks:** geometry feasibility test first (`ug fetch-geometry`, coverage report, choose `osm` versus manual overlay); `OsmCapitalProvider` and scale tiers; layered demand model with forecast error; complete fault catalog and the 28 presets in stages (start with the 10 most important); run store with manifests and hashes; Parquet plus DuckDB for series; chunk-size convergence report.
**Exit gate:** Spec M1 acceptance checks, geometry provenance report, normal week runs, identical hashes for identical manifests.

### Phase B2 (Spec M2): Telemetry, stream, map
**Tasks:** measurement layer upgrade (quantization, jitter, late data); new stream envelope and replay player with seek; design plan for the UI (tokens, wireframes) reviewed before building; shell, theme, i18n scaffolding; map engine v1 (deck.gl) with animated flow and sensors; Scenario Lab basic.
**Exit gate:** Spec M2 acceptance checks, 60 fps on the reference scene, design plan approved.

### Phase B3 (Spec M3): Quality, detection, incidents
**Tasks:** Q01 to Q12, expectation with forecast error, detectors D1 to D3, diagnosis, signature-matrix localization, incident manager and lifecycle, Alerts, Quality Observatory, Case File.
**Exit gate:** Spec M3 acceptance checks.

### Phase B4 (Spec M4): Impact, cost, decision, evidence
**Tasks:** design grid runner, cost engine and sampling, decision engine with CVaR, regret, decision map, evidence kernel and provenance graph, reports, Decision Studio, Evidence Explorer, before and after.
**Exit gate:** Spec M4 acceptance checks, `ug reproduce` verifies a report.

### Phase B5 (Spec M5): Evaluation and ML
**Tasks:** harness, D4 to D6, BattLeDIM track, policy comparison, Evaluation Lab, leakage disclosure.
**Exit gate:** Spec M5 acceptance checks, headline KPI with interval and strongest baseline.

### Phase B6 (Spec M6): Experience layer
**Tasks:** Time Machine with branching, 3D Capital view, wall mode, Executive Brief, command palette, notification center, Economics Lab, Sensor Placement Lab, AR and EN polish, day theme.
**Exit gate:** Spec M6 acceptance checks, accessibility audit.

### Phase B7 (Spec M7): Hardening
**Tasks:** performance, security hygiene, docs, Demo Mode, packaging, final regression.
**Exit gate:** Spec M7 acceptance checks, fresh clone to running demo in one command.

### After the water core passes B5 at minimum
P2 Electricity, P3 District Cooling, P4 Calibration and live (Spec Sections 18 to 20).

### Estimating effort
Each phase is split into sessions of one coherent task group each. If a session cannot finish its tasks, it records state in `PROGRESS.md` and stops cleanly.

## 10. Working with Claude Code on a Pro plan (token and usage hygiene)

Usage on a Pro plan is limited per time window (check the current Claude Code documentation for exact limits). Plan sessions accordingly.

1. **Start each session fresh.** Rely on `CLAUDE.md`, `PROGRESS.md` and the one relevant section of this plan. Use `/clear` between phases and `/compact` if a session grows long.
2. **Do not ask it to read the whole repository.** Use `git ls-files`, `wc -l`, `grep` for symbols, and read only the two or three largest or riskiest files in full.
3. **Plan first, then execute.** Ask for a short plan and approve it. This avoids wasted edits.
4. **Write results to files**, not to chat (`AUDIT.md`, `DECISIONS.md`). They are cheap to re-read later and do not need to be regenerated.
5. **Run tests quietly** (`pytest -q`, truncated output) and fix failures one group at a time.
6. **Commit often.** An interrupted session then resumes cheaply from git and `PROGRESS.md`.
7. **Avoid sub-agent fan-out** unless a task is large and independent.
8. **Use the lighter model for routine edits** if the tool lets you choose, and the strongest model for the audit, hydraulics and architecture decisions.
9. **Batch similar work.** For example, fix all missing-label issues in one pass rather than one per session.

## 11. Stop conditions and escalation

Stop and ask the human when:
- an Honesty Rule seems to conflict with a task,
- a contract change is needed,
- a module is proposed for `REWRITE` or deletion,
- a dependency with a license or cost implication is needed,
- WNTR or a library cannot do something the spec assumes (propose alternatives with trade-offs),
- the audit shows the baseline is mostly unusable (recommend a rebuild plan with reasons and cost, do not start it).

## Appendix A: Characterization (golden) tests

Purpose: detect unintended behavior change during refactoring.

1. For each of the presets `normal`, `holiday`, `heatwave`, `leak_gradual`, `leak_sudden`, `sensor_drift`, `pump_outage` (use the names that exist), run with a fixed seed at reduced duration.
2. Store a compact snapshot in `tests/golden/`: hash of ground-truth series rounded to a defined tolerance, hash of telemetry, list of incidents (type, location, first tick), top-line cost numbers from a fixed assumption set.
3. A test reruns and compares within tolerance.
4. Update a golden file only deliberately, in its own commit that states why the behavior changed.
5. Do not pin behavior that the audit marks as a defect.

## Appendix B: Definition of done for a task

Code and tests written. Tests pass locally and in CI. Contract changes versioned. Every new displayed number has an evidence record and label. `PROGRESS.md` updated. Commit message states what changed and why.
