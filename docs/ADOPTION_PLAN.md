## 0. Purpose

A first implementation of this project exists in `freebuff/`. It was generated by a different AI coding agent (freebuf) from an earlier, smaller prompt. **It is a reference, not the foundation.** We keep it so we can see what was tried, take ideas from it, and learn which traps to avoid. We do not depend on it, shape the architecture around it, or preserve its structure or behavior.

The target is the Master Spec. We will:

1. build the real structure (`platform/`, `domains/water/`, `contracts/`, `assumptions/`, `frontend/`, ...) fresh at the repository root, following the spec;
2. take a short inventory of `freebuff/` to find reusable ideas, working pieces and known pitfalls;
3. reuse a piece of `freebuff/` code only if it passes review and is better than writing it new, and record every reuse (file, what was reused, why) in `docs/audit/DECISIONS.md`;
4. leave everything not reused untouched in `freebuff/` as reference.

Authority order: Honesty Rules, then the Master Spec, then this plan, then the existing code. The existing code has no authority.

## 2. Principles for working with a reference baseline

1. **Build to the Spec, not around freebuff.** The target structure is built fresh. Nothing in `freebuff/` constrains it.
2. **Reuse selectively and on evidence.** A piece is reused only if it passes review (Section 6 checklist), is better than writing it new, and has tests. Each reuse is logged in `docs/audit/DECISIONS.md` with file, what was reused and why.
3. **Golden tests only for reused pieces** (Appendix A). We do not characterize behavior we are not keeping.
4. **Known pitfalls become tests first.** The traps found in the inventory (truth leaking into decisions, unlabeled numbers, non-determinism, wrong WNTR usage; see `docs/audit/PITFALLS.md`) are turned into tests in Phase A1, before the code that could fall into them exists.
5. **Small reversible steps.** One logical change per commit, tests green at every commit.
6. **Verify external APIs** against the installed versions (`ug doctor` once it exists). Generated code often calls APIs that do not exist or have changed.
7. **Old code has no authority.** If code and spec disagree, the spec wins.
8. **One phase per session.** Keep sessions short and resumable. State lives in files (`docs/PROGRESS.md`), not in conversation history.
9. **Decision log.** Every reuse, deletion or change of stance is written to `docs/audit/DECISIONS.md` with a reason.
10. **No deep audit of code we may not use.** Inventory is short. A piece gets a full review only when we propose to reuse it.

## 4. Reuse decision rules

Every piece of `freebuff/` we look at gets one verdict, recorded in `docs/audit/DECISIONS.md`.

| Verdict | When | Action |
|---|---|---|
| `REUSE` | Correct, passes the Section 6 checklist, better than writing it new | Copy into the new structure with attribution to the source file, add tests (including golden tests for the reused behavior), log it |
| `ADAPT` | The idea or logic is right, the implementation or structure is not | Re-implement to the spec, cite the source idea, add tests, log it |
| `REFERENCE` | Interesting, not needed now | Leave in `freebuff/` untouched |
| `AVOID` | A known pitfall (honesty, physics, determinism) | Record it in `PITFALLS.md`; the new code gets a test that would catch it |

Severity scale for pitfalls and any later findings:

| Level | Meaning | Examples |
|---|---|---|
| S0 | Blocks trust | Truth leaks into the stream or decisions, invented probabilities, number shown without a label, non-determinism, wrong hydraulics, missing banner |
| S1 | Major | API calls that do not exist, tests absent for core logic, false alarms on normal runs, double counting in costs |
| S2 | Moderate | Missing contract fields, hard-coded constants, poor structure, weak error handling |
| S3 | Minor | Style, naming, comments |

## 6. Review checklist (for the short inventory, and for any piece proposed for reuse)

Used lightly in Phase A0 to find pitfalls, and in full on a piece before it is reused. For each item record `OK`, a finding with severity and evidence (`file:line` or command output), and a verdict (Section 4).

### 6.1 Network and scenarios
- Network is deterministic for a given seed. `network_version` is a content hash.
- Connectivity, no isolated junctions, units documented (head in metres, flow in m3/h).
- Minimum pressure at peak demand is acceptable. Tanks do not overflow or starve over a 7-day normal run.
- A `NetworkProvider` abstraction exists, or note its absence.
- Scenario schema: validated ranges, unknown fault types and unknown sensor or pump ids rejected, times inside the horizon, versioned.

### 6.2 Simulation (WNTR)
- Every WNTR call exists in the installed version (introspect, do not trust).
- Pressure-driven demand is actually enabled and the chosen simulator supports it with leaks.
- Pipe leaks: split-node approach is correct (flows conserved, leak area units correct).
- Gradual leaks: piecewise chunking hands over tank levels and pump states between chunks, fault onsets land on the configured tick, and a chunk-size convergence check exists.
- Pump outage and standby switching work and are tested.
- Fault-free baseline run uses the same demand settings, and this assumption is documented.
- Runtime for a 48 h run is measured.
- Same config plus seed gives identical output (hash it twice).

### 6.3 Sensors and stream
- Noise is seeded, with independent streams per sensor. Drift, stuck, dropout, offset behave as described. Dropout produces missing readings, not zeros.
- **Truth never appears in the stream, in detector inputs, or in decision inputs.** Search the code for every place truth and hidden fault tags are read.
- Message format matches the contract. Pause, resume, speed, seek work.

### 6.4 Quality, detection, incidents
- Thresholds are configurable. Each check has a unit test.
- Residuals are normalized with sigma that includes expectation-model error, not sensor noise alone. Persistence or CUSUM exists.
- False alarms on `normal`, `holiday`, `heatwave` over at least 5 seeds, **including a case where the demand forecast is wrong**. Record the count.
- Diagnosis returns `unknown` for ambiguous cases. No percent confidence without a defined statistic.
- Incident grouping yields one incident per root cause. Merge and split behavior is tested.

### 6.5 Impact, finance, decision, evidence
- Impact runs start from a state snapshot on copies of the network, and use telemetry or estimated state, not truth.
- Each money line equals one physical quantity times one unit price. No double counting.
- Assumptions have unit, range, version and verified flag, and every editable assumption actually drives a result. No invented probabilities presented as findings (including equal weights over variants).
- Monte Carlo output is labeled "conditional on assumed ranges".
- Decision engine includes break-even and sensitivity. A scenario with negative benefit recommends `monitor`.
- Every number the UI shows has an evidence record and a label. No LLM in calculations.

### 6.6 API, storage, frontend, ops
- Endpoints match the contract. Errors are structured. No truth over WebSocket; the truth endpoint is separate and gated.
- Time series are stored in a way that scales to long runs. Run manifests exist.
- Frontend: honesty banner on every page, label chip on every number, "show twin truth" toggle separate from operator view, no CDN dependencies, builds cleanly, no hard-coded demo numbers.
- `docker compose up` works offline. README commands work from a fresh clone.
- Tests exist, are meaningful, and pass. Linting and type checks run.
- Secrets, licenses and dependency pinning reviewed.

## 10. Working with Claude Code on a Pro plan (token and usage hygiene)

Usage on a Pro plan is limited per time window (check the current Claude Code documentation for exact limits). Plan sessions accordingly.

1. **Start each session fresh.** Rely on `CLAUDE.md`, `PROGRESS.md` and the one relevant section of this plan. Use `/clear` between phases and `/compact` if a session grows long.
2. **Do not ask it to read the whole repository.** Use `git ls-files`, `wc -l`, `grep` for symbols, and read only the two or three largest or riskiest files in full.
3. **Plan first, then execute.** Ask for a short plan and approve it. This avoids wasted edits.
4. **Write results to files**, not to chat (`PITFALLS.md`, `DECISIONS.md`). They are cheap to re-read later and do not need to be regenerated.
5. **Run tests quietly** (`pytest -q`, truncated output) and fix failures one group at a time.
6. **Commit often.** An interrupted session then resumes cheaply from git and `PROGRESS.md`.
7. **Avoid sub-agent fan-out** unless a task is large and independent.
8. **Use the lighter model for routine edits** if the tool lets you choose, and the strongest model for architecture, hydraulics and honesty-critical decisions.
9. **Batch similar work.** For example, fix all missing-label issues in one pass rather than one per session.
10. **Do not audit code we may not use.** Read `freebuff/` only to take a reuse decision.

## Appendix A: Golden (characterization) tests for reused pieces

Purpose: when a piece of `freebuff/` is reused, pin the reused behavior so later changes cannot alter it unnoticed. Not applied to anything we do not reuse.

1. For the reused function or module, run representative inputs (for scenario code, presets such as `normal`, `holiday`, `heatwave`, `leak_sudden`, `sensor_drift`, `pump_outage`, with a fixed seed at reduced duration).
2. Store a compact snapshot in `tests/golden/`: hash of outputs rounded to a defined tolerance, plus any lists or numbers that matter.
3. A test reruns and compares within tolerance.
4. Update a golden file only deliberately, in its own commit that states why the behavior changed.
5. Do not pin behavior that `PITFALLS.md` marks as a defect.

## Appendix B: Definition of done for a task

Code and tests written. Tests pass locally and in CI. Contract changes versioned. Every new displayed number has an evidence record and label. Any reuse from `freebuff/` is logged in `docs/audit/DECISIONS.md`. `PROGRESS.md` updated. Commit message states what changed and why.
